# ShiftTracker UX/UI Design Rules

## 1. Главный продуктовый принцип

Каждый экран отвечает на один основной вопрос и предлагает одно главное действие.

Не добавлять новый блок на существующий экран только потому, что там осталось место. Если функция имеет самостоятельный смысл, открывать отдельный экран, drawer или bottom sheet.

## 2. Mobile-first

- мобильный интерфейс не является уменьшенным desktop-dashboard;
- один раздел движется преимущественно в одном направлении;
- не пытаться поместить всё на один экран;
- основной текст: 16–17 px;
- подписи: 13–14 px;
- зоны нажатия: минимум 44×44 px;
- самостоятельные блоки разделять отступами 20–24 px;
- не уменьшать текст ради плотности.

## 3. Навигация

Для сотрудника: Главная / История / Выплаты / Профиль + отдельная кнопка создания.

Для администратора: Главная / История / Управление / Профиль + отдельная кнопка создания.

- навигация означает «куда перейти», кнопка «+» — «что создать»;
- создание смены не должно выглядеть как вкладка;
- dock содержит максимум четыре основных раздела;
- активна только одна вкладка;
- в полноэкранных формах dock можно скрывать;
- состав основных вкладок не должен хаотично меняться.

## 4. Контекстные действия

- сотруднику «+» открывает создание смены;
- администратору «+» может открывать короткий bottom sheet;
- максимум три контекстных действия;
- вторичные действия не конкурируют с главным;
- опасные действия визуально отделены;
- жесты и long press используются только дополнительно.

## 5. Bottom sheets и drawers

На мобильном bottom sheet используется для фильтров, выбора точки, выбора периода и коротких контекстных действий.

В web-admin drawer/side panel используется для редактирования сотрудника, редактирования точки и просмотра деталей объекта. Короткое действие не нужно уводить на отдельную страницу, если важно сохранить контекст.

## 6. Карточки

- одна карточка — один самостоятельный объект;
- избегать card inside card;
- не оборачивать каждую цифру в отдельный контейнер;
- группировать данные отступами и разделителями;
- не использовать одинаковые большие карточки для всей информации;
- не добавлять декоративные KPI-карточки без продуктовой ценности;
- в web-admin таблицы и списки предпочтительнее набора декоративных карточек.

## 7. Состояния интерфейса

Проектировать не только заполненное состояние. Обязательно учитывать первый вход, отсутствие смен и выплат, пустой результат фильтра, loading, API error, permission denied, inactive user, successful save и successful payment record.

Empty state должен объяснять, почему данных нет, показывать следующий понятный шаг и не заполнять экран множеством пустых карточек.

## 8. Визуальный стиль

Использовать спокойный нейтральный интерфейс, молочный/тёплый светлый фон, графитовую тёмную тему, сдержанный синий или кобальтовый акцент, чистую типографику и настоящую визуальную иерархию.

Не использовать фиолетовый как основной акцент, фиолетово-синие AI-градиенты, кислотные цвета, чрезмерное свечение, повсеместный glassmorphism, слишком много pill-бейджей, emoji вместо иконок, типовой AI-generated SaaS, дизайн дешёвой CRM из 2010-х и декоративные графики без реальных данных.

## 9. Тексты

- русский интерфейс;
- короткие человеческие формулировки;
- избегать псевдоделового AI-копирайтинга;
- не добавлять объясняющий абзац под каждым заголовком;
- не злоупотреблять длинными тире;
- инструкции показывать только там, где пользователь действительно может запутаться;
- использовать «удержания», а не «штрафы»;
- «Выплачено» использовать только для фактического PayrollPayment;
- «Начислено» использовать для зафиксированного расчёта;
- «Предварительно» использовать для ещё не зафиксированных начислений.

## 10. Layout определяет человек

Перед UI-изменением определить роль пользователя, главный вопрос экрана, главное действие, порядок блоков, что скрывается глубже и какие данные реально доступны.

Если layout не определён, сначала предложить структуру и остановиться, а не реализовывать большой redesign.

## 11. Правила для Mini App

- Главная сотрудника: текущее финансовое состояние, последняя смена и только реальные события, требующие внимания;
- История: только смены, фильтры через bottom sheet;
- Выплаты: текущее начислено / выплачено / осталось, последняя выплата и полная история на отдельном экране;
- Новая смена: одна задача, dock скрыт, фиксированная кнопка сохранения;
- Управление: мобильное меню разделов, где утверждение, команда, точки, расчёты и аудит открываются как самостоятельные экраны.

## 12. Правила для web-admin

- не копировать мобильный интерфейс на desktop;
- использовать sidebar, таблицы, списки, фильтры и drawers;
- не превращать обзор в сетку одинаковых KPI;
- обзор показывает только реальные задачи и состояние бизнеса;
- не использовать fake data, fake charts и fake analytics;
- рабочие экраны важнее эффектного Dashboard;
- desktop должен выглядеть как современный операционный инструмент, а не дешёвая CRM.

## 13. Безопасный процесс внедрения

- один UI-коммит — один экран или один самостоятельный элемент;
- не переделывать всё приложение одним промптом;
- не менять backend во время косметической задачи;
- сначала структура, затем визуал;
- проверять light и dark theme;
- проверять ширину 390 px;
- проверять desktop/tablet для web-admin;
- проверять отсутствие перекрытия dock;
- не добавлять новые UI-библиотеки без необходимости;
- не использовать hardcoded colors;
- использовать CSS variables.

## 14. Checklist перед завершением UI-задачи

- понятна ли задача экрана за 3 секунды;
- есть ли одно главное действие;
- нет ли дублирования навигации;
- нет ли карточек внутри карточек;
- не слишком ли много текста;
- нет ли типичных AI-градиентов и декоративных KPI;
- все ли зоны нажатия достаточного размера;
- есть ли loading/error/empty states;
- работает ли light/dark;
- не выглядит ли результат как типовой vibe-coded SaaS;
- не сломана ли существующая логика.
